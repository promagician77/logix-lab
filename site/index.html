Mutation testing: do the tests notice a bad edit?

Every possible one-instruction edit was made to the program, one at a time, and the tests were run against each edited copy. The edits: XIC swapped for XIO, a comparison boundary moved, a contact deleted, a branch leg removed, OTE swapped for OTL, a constant or timer preset doubled, a rung deleted. Edits the engine's verify step rejects (wrong operand type, broken rung) were discarded. A test set "catches" an edit if any test fails.

Troubleshooting: six classic site edits, seeded on purpose

Each bug below was put into the working program on its own, then checked two ways. First, a linter reads the L5X like a reviewer would. Second, the scenario tests run the program. The linter finds structural mistakes in seconds without running anything. Behaviour bugs need the tests. The clean program has — lint findings.

Run hours lost by a self-resetting 1 s timer (B-5), by scan time

Measured over 1 h of running in the scan model: the reset scans lose time on every 1 s cycle, so the error grows with scan time. The shipped program counts in a 1000 ms periodic task and was exact to the second at every scan time tested (scenario F15).

Program structure and standards

Tasks, programs, routines

MainTask (continuous) → MainProgram → R00_Main calls each routine in a fixed order. T1000ms (periodic, 1000 ms) → Totals.

ProgramRoutinePurposeRungs

Conventions used

  • I/O mapped once (R01 / R30). Logic never touches module tags, so a card move is a two-rung edit.
  • UDTs per device (UDT_Pump, UDT_Alarm): one-shots, timers and status live inside the instance, so copying pump 1's logic for pump 2 cannot share a storage bit.
  • One OTE per bit. Latches only for faults, each with a reset condition.
  • HMI handshake: the HMI sets request bits; the PLC acts and clears them, and clears all of them on first scan. Maintained HMI bits are marked "(maintained)" in the description.
  • Setpoints validated before use; the logic only reads the SPV_ copies.
  • Alarms: condition → on-delay → active → unacknowledged, from one template.
  • Totals in a periodic task, not self-resetting timers.
  • Every behaviour has a test, and the tests run against the L5X itself.

Into Logix Designer

  • L5X: Logix Designer opens .L5X files with File › Open and builds a project from them. This file targets a CompactLogix 1769-L33ER at v32. Once open, add the I/O modules and point R01 and R30 at the module tags.
  • Single rungs: every rung's text above is Rockwell neutral text, so you can paste it into the rung editor's ASCII view.
  • HMI: the screen here shows the design. In FactoryTalk View ME/SE it maps one-to-one to direct references such as {[PLC]P1.Fault} (see hmi_tags.csv).
  • Independent read: the open-source l5x Python library opens the file and reads all 58 tags, both programs, the UDT BOOL members, timer presets and descriptions (tools/check_l5x.py).
  • Honest scope: the L5X has not been opened in Logix Designer here, because there is no Rockwell licence in this environment. The scan engine implements the instructions this program uses, following Rockwell's instruction reference. It is a test bench, not a controller emulator: no I/O update timing, no task overlap, no fault routines.

Measured

All 25 scenario results, the mutation study, the lint findings and the run-hour drift were produced by running the shipped L5X in the scan engine against the plant model. The figures on this page are loaded from those result files.

Not measured

A real controller, real I/O, a real HMI runtime, network behaviour and real pump hydraulics. Plant numbers (wet well 4 m², pumps 18 / 30 L/s) are illustrative. The scan engine is a test tool and does not replace Logix Designer's Verify or an on-site FAT.
